# Force 4625 bench validation — 2026-09-10

Port 5 was identified from fresh switch LLDP as Force 4625, advertising 5.9.0.
PoE cycling the verified `ether5` did not clear credential rejection. The
operator then held the reset button for approximately ten seconds. Subsequent
provisioning and a separate paused-service login confirmed factory access.

The first firmware stage failed before configuration/secrets. The target file
was `ePMP-AX-v5.11.1.img`; the explicit fallback upload reported curl exit 52
(empty reply). The later authenticated config readback reports active software
5.9.0 and alternate software 5.9.2. Earlier coarse discovery reported both as
5.9.0. **The 5.9.2 report does not prove an upload changed that bank**: it does
not match the attempted image, and no completed 5.11.1 transition is established.

A separate, confirmed handler defect made fallback unreliable: legacy upload
failure deleted the shared authentication cookie, while the fallback reused
that missing path. A live fallback process was observed with no cookie file.
The scoped correction keeps cleanup in `disconnect()`, preserves the session
for fallback, keeps the authenticated upload URL off process arguments, and
logs curl exit status without raw response/secret text.

The new regression test fails the first upload and asserts that fallback still
has its cookie. The reconciled full suite passed **951 tests, 4 skipped**;
focused Cambium tests also passed against the deployed source snapshot.
Only the uploader correction was deployed, after every port was idle. The
reconciled application was not deployed. The provisioner and kiosk were restarted.

The post-fix hardware run still failed at the first firmware step: both legacy
and explicit uploads returned curl exit 52. Login passed; configuration and
secret application did not run. The device-served 5.9.0 JavaScript was saved
privately for reference. It uses `local_upload_image` with the `image` form
field and polls `get_upload_status`; neither newer explicit-upload endpoint
appears in that bundle. Its `clear4update` preparation is skipped for AX SKUs,
so adding that operation to this AX device is not justified by this capture.
The cookie correction alone does not resolve the hardware failure. A browser
upgrade capture on this exact device/firmware is the next evidence needed to
compare a working request or establish that the GUI also fails.

## Browser reconstruction

The supplied `cambium4616.upgraderesetconfig.har` already covers a successful
4616 upgrade from 5.11.0 to 5.11.1. Its reviewed request sequence is in
[`ePMP_4616/5.11.1/capture-summary.md`](../bench-evidence/cambium/ePMP_4616/5.11.1/capture-summary.md).
It establishes upload, explicit upgrade with `type=device&debug=true`, status

A Chromium/Playwright investigation on the provisioner opened the actual
4625 interface and recorded private HARs. The factory UI displayed an admin
password prompt. Attempts to proceed subsequently encountered application
login failure: HTTP 200 with `success: 0` and message key
`max_user_number_reached`. A verified port-5 PoE cycle did not establish that
the lockout was cleared; a subsequent browser login returned the same key.
Explicit logout requests were also sent for sessions from our own captures.
No successful browser firmware upgrade is established.

The reconstructed sequence to complete is: log in; complete the forced admin
password prompt using the stored standard; open **Tools → Software Upgrade**;
select the reviewed AX firmware file; start the upgrade; wait for the device's
completion status; then reboot and independently read both firmware banks.
For 5.9.0, the device JavaScript selects `local_upload_image` and
`get_upload_status`. Keep this reconstruction separate from an executed,
successful hardware transition.

Browser automation must bind every device connection to the selected VLAN
interface. When Chromium uses an interface-bound proxy, explicitly disable
its implicit link-local bypass (`bypass: "<-loopback>"`). Earlier diagnostic
attempts without this explicit setting are not isolation-qualified evidence.
Some diagnostic runs replayed the device's previously captured static UI
assets to avoid asset-download timeouts; label that replay in any derived
evidence. Raw captures and their hashes are retained in
`browser-capture-manifest.private.json` beside the other private evidence.

Always check application login success and explicitly log out during cleanup.
HTTP 200 and closing a browser do not establish successful authentication or
release its server-side session. An unattended browser harness is still a
development aid here, not a qualified provisioning path.

Six retained browser HARs contain no configuration/password write, firmware
upload, or reboot request. After capture cleanup, `provisioner-web` and
`kiosk-watchdog` were restored and confirmed active. Documentation checks pass.

## Controlled PoE recovery check

A subsequent controlled test confirmed recovery. Automatic provisioning was
paused and the diagnostic browsers were closed. With `ether5` PoE off for ten
seconds, the switch reported link down and an interface-bound HTTP probe no
longer received a response. PoE was restored to `auto-on`. After boot, one
fresh factory login succeeded and authenticated configuration readback worked;
the banks still reported 5.9.0 and 5.9.2. The test session was explicitly
logged out. Evidence is in `verified-power-cycle.private.json`,
`after-verified-cycle.private.json`, and `after-verified-cycle-summary.json`.

The earlier browser retries did not isolate the interval between reboot and
new session creation. They must not be cited as evidence that a real PoE
restart fails to clear session exhaustion. Recovery SOP: pause automated
clients, close diagnostic browsers, verify both power/link loss and loss of
device reachability, restore power, wait for boot, then verify a single fresh
login and readback before resuming other clients. This recovery check does
not establish firmware-upgrade or provisioning success.

Private captures and deployment hashes:
`/var/lib/provisioner/bench-evidence/cambium/ePMP-4625/live-2026-09-10/`.
The earlier port identification/reset records are under the sibling private
`port5-identification-2026-09-10` directory at the evidence root.

This model is **not qualified**: successful dual-bank upgrade, baseline/secrets
readback, fresh standard-login/default-login rejection, AP/VLAN/traffic and
cold-power persistence remain acceptance gates. Do not mark it passed based
on model detection, an upload response, or software tests.

After the operator confirmed a reset, a fresh factory login succeeded on the
port-5 4625. Authenticated preflight again reported active 5.11.1 and alternate
5.9.0. Automatic provisioning was stopped while these operations ran. Earlier
login failures included transport timeouts; they do not establish rejection of
the factory credentials.

The literal legacy upload request ended with curl exit 52 after HTTP 100

Further inspection of entry 321 in the supplied HAR found the post-upgrade
`cambium.399d22adfa.js` UI bundle: it contains `upload_sw_image_local`,

old endpoint sequence is not a supported second-pass assumption on 5.11.1.

The explicit upload was attempted with the `image` multipart field and
`Expect` suppressed. It also ended with curl exit 52, before the explicit
upgrade trigger. A 512 KiB/s capped retry failed the same way. TCP inspection
showed repeated retransmissions and little acknowledged upload data, rather

not resolve the failure; do not describe it as a proven handshake fix.

A controlled PoE cycle between attempts verified port-5 link loss and restored
power with competing automatic clients paused. It restored responsive login
and configuration readback, but did not resolve uploads. Snapshot Ethernet
counters showed two receive FCS/alignment errors on ether5 and no reported

No explicit flash trigger or post-upload reboot was issued. The last confirmed
banks remain 5.11.1 / 5.9.0. The next physical isolation check is a known-good
cable, followed by another verified bench port if needed. This remains an
unqualified second-bank update, not a provisioning pass. Sanitized preflight
metadata is retained under the private `second-bank-2026-09-11/` evidence

## Operator review invalidated the narrow baseline acceptance — 2026-09-11

The operator found EAP-TTLS still enabled alongside WPA2, management VLAN 12
priority needing correction to 0, and anonymous reporting needing disablement.
The earlier 25-field check and WPA-key match did not cover these selectors.
They must not be cited as proof of complete security/baseline acceptance.
The unit was no longer detected on bench port 4 during this audit, so its
operator-corrected configuration has not yet been independently read back.

The captured 5.11.1 UI defines `wirelessSecurityMethod` as an inverted bitmask:
open is bit 0, WPA2 bit 1, EAP-TTLS bit 2. WPA2 only is **5**, not 1 (which
leaves WPA2 and EAP-TTLS available). `wirelessInterfaceEncryption=2` selects
AES-256; it does not select WPA2-only authentication. Management VLAN priority
is `mgmtVLANVP=0`. The UI's Share Anonymous Crash Reports control is
`crashReporterEnable=0` when disabled.

A dated policy witness records these corrections without rewriting historical
captures: `bench-evidence/cambium/policy-correction-2026-09-11.json`. Historical
4518 captures use authentication mask 5 but reporting 1; 4616/300 captures use
mask 1 but reporting 0. This disagreement is why process captures cannot each
be treated as a complete current standard.

Both tracked SM templates also omitted four fields already declared in the
handler's fleet contract: `mgmtIFEnable=0`, `networkBridgeIPAddressMode=2`,
`mgmtIFIPAddressMode=2`, and `syslogServerTypeFirst=1`. The first disables the
separate management interface; the two address-mode settings select DHCP; the
last selects the standard syslog transport. The template-driven verification
set omitted them too. Templates now include the complete declared policy,
and tests require that completeness plus readback detection of selector drift.

The firmware result stands. Full corrected-baseline, power-cycle and RF/VLAN
acceptance must be repeated against the expanded policy; the earlier partial
acceptance is superseded for those settings.

model and applies it atomically with account enablement. Successful provisioning
requires a fresh installer login as well as the existing standard-admin proof.
